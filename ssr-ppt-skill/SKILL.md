# SSR-PPT-SKILL

把需求、证据、叙事结构、逐页策划和视觉制作连接起来，交付重点清楚、让人记住、用户能继续修改的演示文稿。视觉表达服务于内容和使用场景；目标不只是没有错误，而是有明确的视觉概念和值得截图的高潮页。

本文件中的 `references/`、`scripts/`、`assets/` 路径都相对于本 Skill 所在的目录。

## 使用原则：推荐优先，不硬套

本 Skill 提供两类东西：

- **方法**：找焦点、定构图、排节奏、做验收。
- **推荐资源**：风格配方、版式原型、字体搭配、图表做法。每个配方和原型都先写明“适用”与“不适用”。

使用推荐资源时：

- 内容合适就优先参考。
- 不合适就不用，直接按方法从内容出发设计。
- 资源可以修改、组合，清单也不封闭；遇到新情况可以设计新的方案，效果好的在全套中复用。
- 不为了套用资源而凑内容、删内容或扭曲内容。

衡量标准是演示是否好看、让人记住、内容准确，而不是用到了多少推荐资源。策划稿中写明参考了什么、改了什么；没有参考的写“自定”即可，不需要额外理由。

## 执行与交互

- 使用用户已经提供的受众、目的、资料、总页数、品牌、模板和格式，不重复询问。读取已有文件只为完成当前任务。
- 需求足以制作时，说明必要假设后连续完成资料整理、大纲、策划、制作、验收和交付。大纲、策划稿和方向比较都是内部中间产物，不是强制确认关卡。
- 只有缺失信息会实质改变结果时才提问，例如受众与用途无法推断、要求引用却缺少关键数据、指定模板尚未提供。集中询问，同时继续不依赖答案的工作，不把等待当作批准。
- 页数、一般风格等可推断事项自行判断。精确的 N 页包含封面与结束页，不额外添加。用户说“只看大纲”“先给样稿”时止于该阶段。
- 用户未指定格式时默认交付 HTML 和 PPTX；只要一种时只做该格式。两种格式使用同一策划稿和数据，不承诺转换后逐像素一致，也不承诺保留 HTML 动画。
- 默认由当前智能体完成，不强制调用其他模型、外部 CLI 或子智能体。Inner Web Brain / Web Brain 仅在用户为当前任务明确要求时使用。
- 只做本地制作和验证。遵守现有授权与依赖约束，不部署、不推送，不覆盖未授权的原文件。

## 运行环境

| 环境 | HTML 检查 | PPTX 制作 | PPTX 渲染 | 查看图像 |
|---|---|---|---|---|
| Codex 桌面 | 浏览器工具或 Playwright | 官方 `presentations` Skill 与 `@oai/artifact-tool` | 官方渲染与 finalizer | 图像查看能力 |
| Claude Code | `scripts/preview.py html`（Playwright + 本机 Chrome / Edge），或会话中可用的浏览器工具 | 新建用 PptxGenJS；修改已有文件或模板用 python-pptx | `scripts/preview.py pptx`（LibreOffice → PDF → PNG） | 用 Read 读取 PNG |
| 其他 | 已有的浏览器自动化工具 | 已安装的原生 PPTX 库 | 可用的渲染器 | 可用的看图方式 |

- 需要 Python 包（fonttools、brotli、playwright、Pillow、PyMuPDF、python-pptx）或 npm 包（pptxgenjs）时，先检查是否已安装。
- 缺少时可安装到私有构建目录（npm）或当前用户的 Python 环境，先说明用途；不修改用户项目的依赖清单。
- 无法安装或无法联网时，报告缺项与受影响的验收项。

## 1. 建立需求与证据

把主题、受众、演示目的、关键内容、篇幅、视觉约束和交付格式简短记入策划稿开头。

优先整理用户提供的资料。只有任务需要外部事实、时效信息或用户要求检索时才研究，使用当前环境可用的搜索与阅读工具，不绑定某一家服务。数字保留单位、时间、口径和来源；区分事实、计算结果、假设与建议。不能把缺失资料补成确定事实。

有外部资料时保存 `sources.md`，用简短来源标识关联到相关页面和 PPTX 备注；HTML 中也提供可找到的来源链接。纯用户材料无需另建搜索流程。

## 2. 大纲与策划稿

读取 [references/planning.md](references/planning.md)。先决定每页的目的、顺序和能量（高冲击 / 标准 / 密集 / 呼吸），再做视觉设计。报告与说服场景适合结论先行；教学或故事按理解顺序组织，不强套目录和金字塔结构。

必须保存逐页 `planning.md` 并随成品交付；一页任务用短版，修改已有文稿时只更新受影响的页面。策划要写清核心信息、依据、视觉焦点、阅读顺序、版式意图与可编辑对象，不能只有页标题或笼统的风格词。除非用户要求，不额外生成策划用的 PPT 文件。

## 3. 定义视觉方向

新建或美化版式时读取 [references/art-direction.md](references/art-direction.md)，并按其指引读取：

- [references/style-recipes.md](references/style-recipes.md)：13 套风格配方，各自写明适用与不适用。有贴切的就选作起点，并结合主题改编色彩、母题和尺度；没有贴切的就按 art-direction 的方法自定方向。
- [references/layouts.md](references/layouts.md)：22 个版式原型，各自写明适用与不适用。作为单页构图的起点，可以修改、组合；没有合适的就自定构图。
- [references/typography.md](references/typography.md)：字体选择与获取、字号阶梯、中文排版、HTML 字体嵌入、PPTX 字体策略。
- [references/anti-patterns.md](references/anti-patterns.md)：平庸与“AI 味”反模式，策划时避开，验收时对照。
- [references/imagery.md](references/imagery.md)：图片、生成图、图标，以及没有素材时的图形处理。
- [references/charts.md](references/charts.md)：图表选型与美化默认值，HTML 与原生 PPTX 各自的实现要点。

用户模板、品牌或参考优先。没有参考时，自主确定一个具体的视觉概念，按 art-direction 的格式写进策划稿：概念、配方与改编（或自定）、参考调性、色彩、字体、字号、网格、形状语言、图片处理、高潮页和禁用项。局部文字修改沿用已有视觉体系。

先决定每页最需要被看见的内容，再选择构图：可以参考适用的版式原型，也可以自定。统一字体、对齐和色彩语义，按叙事安排密度与节奏；为比较而有意重复可以保留。高潮页在策划时就确定，并优先投入。

较长演示（约 6 页以上）先按 [references/visual-review.md](references/visual-review.md) 做方向比较：封面和一个关键页各做 2–3 个明显不同的方向，并排渲染后选定。然后完成代表页（封面、典型内容页、数据或复杂信息页，只选实际包含的页型），校准后再推广到全套。双格式任务要确认关键构图在两种格式中都成立。方向比较和代表页都属于内部步骤，不增加确认关卡，也不增加交付页数。

先让静态画面成立，再按需增加 HTML 动效。文字、图表和需要编辑的对象保持原生。

## 4. 制作交付格式

- **HTML**：读取 [references/html.md](references/html.md)。默认单文件离线可打开。把 `assets/player.css` 与 `assets/player.js` 内联进成品，它们负责翻页、进度、逐步揭示、概览、备注、全屏与打印，不限定页面视觉。用 `scripts/embed_fonts.py` 子集化并内联设计字体。
- **PPTX**：读取 [references/pptx.md](references/pptx.md)。按“运行环境”选择工具。正文、表格、数据图表及要求可编辑的示意图使用原生对象。按 typography 为每段文字设置中文东亚字体，并用 `scripts/set_theme_fonts.py` 设置主题字体，让图表中文和新增文本也使用设计字体。
- **两者都要**：共享页数、顺序、核心文字、数据与视觉规则，分别制作、分别验收。可以复用结构化的页面描述，但不把 HTML 截图或整页 SVG 塞进 PPTX 当作可编辑交付。

## 5. 实际预览验收

**生成文件、解析成功、代码检查和模型评分都不能替代实际预览。**

制作或美化页面时读取 [references/visual-review.md](references/visual-review.md)，检查焦点、层级、构图、素材、反模式、整套节奏，并做出彩检查。只改局部内容时，重点检查受影响的页面及其与前后页的连贯性。

1. 对照策划稿检查内容覆盖、总页数、事实、单位和引用；移除未解决的占位与制作过程文案。
2. HTML 用浏览器实际打开最终文件：
   - 等待字体与图片加载，逐页查看完全揭示后的页面。
   - 测试翻页、逐步揭示、边界页、概览、全屏（环境支持时）与打印。
   - 检查控制台与资源请求，确认无本次引入的错误，并能离线使用。
   - 检查常用宽屏和较小视口。
3. PPTX 导出后重新读取最终文件并逐页渲染，逐张查看完整尺寸的图像。
4. 两种格式都做缩略总览，检查整体节奏；再看完整页面的重点、留白、中文排版、图表与素材。缩略图不能代替逐页检查重叠、截断、字体、标签和模板一致性。
5. 检查 PPTX 原生对象及图表数据，排除整页图片伪装。在测试副本中修改代表性的文字、表格单元格和图表值，保存、重新打开并渲染，确认修改生效。最终文件不保留测试改动。
6. 发现本次引入的问题就修复，重新导出并检查受影响的页面；全局字体或主题改变时重新查看全套。两种格式各自通过才算双格式完成。

缺少浏览器、渲染器或必要的导出能力时，保留已完成的产物，明确指出哪项验收尚未完成；不得悄悄改成交付整页图片，不得声称已完成实际预览。只有确实在 PowerPoint 中打开和操作过，才能报告 PowerPoint 实机验证；LibreOffice 渲染要如实报告为 LibreOffice。

## 6. 交付

交付用户需要的 `index.html`、`deck.pptx` 与 `planning.md`，做过研究则附 `sources.md`；PPTX 使用非系统字体时附字体文件或安装说明。名称可按主题调整。生成源码、截图和验收记录留在私有构建目录，用户要求时再交付。保持策划稿与最终版本一致。

简短说明完成的格式和使用方式（例如 HTML 的快捷键），提供真实的绝对路径；有影响使用的限制时准确说明。在 Codex 中展示成品有帮助时，可以用 `open_in_codex` 打开 HTML，但打开面板不算完成预览验收。达到当前要求后停止。
