# SSR-PPT-SKILL

把需求、证据、叙事结构、逐页策划和视觉制作连接起来，交付重点清楚、让人记住、用户能继续修改的演示文稿。视觉表达服务于内容和使用场景；目标不只是没有错误，而是有明确的视觉概念和值得截图的高潮页。

本文件中的 `references/`、`scripts/`、`assets/` 路径都相对于本 Skill 所在的目录。

## 使用前提

本技能只供能直接查看图片的模型使用：制作和验收都要实际查看渲染后的页面。当前模型不能看图时，直接停止，告诉用户本技能需要能看图的模型，不做策划或成品。OCR 文字、文件名、XML／DOM、自动检查结果或另一个模型的描述，都不能代替看图。

## 使用原则：推荐优先，不硬套

本 Skill 提供两类东西：

- **方法**：找焦点、定构图、排节奏、做验收。
- **推荐资源**：风格配方、版式原型、字体搭配、图表做法、图标库。每个配方和原型都先写明“适用”与“不适用”。

使用推荐资源时：

- 内容合适就优先参考。
- 不合适就不用，直接按方法从内容出发设计。
- 资源可以修改、组合，清单也不封闭；遇到新情况可以设计新的方案，效果好的在全套中复用。
- 不为了套用资源而凑内容、删内容或扭曲内容。

衡量标准是演示是否好看、让人记住、内容准确，而不是用到了多少推荐资源。策划稿中写明参考了什么、改了什么；没有参考的写“自定”即可，不需要额外理由。

## 开场两问

先继承用户已经说过的偏好：

- “遇到问题可以问我”：第 1 问已答“允许”。
- “需求明确时连续完成”：只表示需求清楚后不必逐步确认，不等于不许提问，第 1 问照常问。
- “不要问我”“全部你自己判断”等针对整个任务的说法：第 1 问已答“不允许”。只针对某件事的“你自己判断”（如“配色你自己判断”）只把那件事交给你，第 1 问照常问。
- “尽量用图”“多用图标和图片”：第 2 问已答“图示优先”。

尚未明确的，在开始制作前用同一条消息按顺序问，已明确的那一问省略：

1. 是否允许我先询问几个问题？（允许则遇到关键缺口时逐个询问；不允许则由我自行判断并连续完成。）
2. 表达方式选哪种：**图示优先**（能用图片、图标、示意插画代替的文字尽量代替，页面只留结论、关键数字和短标签，解释放备注），还是**图文均可**（按内容选择，接受文字较多的页面，适合会前分发或存档阅读）？

两问都有答复后再开始制作；不把沉默当作选择，等待时可以先读材料、做不依赖答案的准备。用户明确不让问、又没说表达方式时，按图示优先制作，并在策划稿开头写明。

## 执行与交互

- **允许询问**：先读材料，一次问一个会实质影响结果的问题，例如受众与用途无法推断、要求引用却缺少关键数据、指定模板尚未提供；同时继续不依赖答案的工作。需求充分后直接制作。
- **不允许询问**：按用户要求 → 材料／品牌／模板 → 目标与场景 → 可调整的设计假设做决定，过程不追问。事实不足时标明缺口或降低结论强度。
- 使用用户已经提供的受众、目的、资料、总页数、品牌、模板和格式，不重复询问。大纲、策划稿和方向比较都是内部中间产物，不是确认关卡。
- 页数、一般风格等可推断事项自行判断。精确的 N 页包含封面与结束页，不额外添加。用户说“只看大纲”“先给样稿”时止于该阶段。
- 用户未指定格式时默认交付 HTML 和 PPTX；只要一种时只做该格式。两种格式使用同一策划稿和数据，不承诺转换后逐像素一致，也不承诺保留 HTML 动画。
- 默认由当前智能体完成，不强制调用其他模型、外部 CLI 或子智能体。Inner Web Brain / Web Brain 仅在用户为当前任务明确要求时使用。
- 只做本地制作和验证。保留用户原件；不部署、不推送，不覆盖未授权的文件。

## 表达方式

**图示优先**（未选择时的默认）：凡是能用图来表示的文字信息，尽量用图来表示。这里的“图”首先指好看的图片、图标和示意插画，不是塞满文字的信息图。

- **图标**：表头、卡片标题、流程节点、关键数字旁可以配图标，帮助识别和美化。用 `assets/icons/` 的线性图标（索引见 `assets/icons/INDEX.md`），全套一种风格、一种线宽、一两种颜色；不用 emoji。
- **配图**：讲主体、场景或产品时配图。可以上网搜索授权合适的照片或插画，例如讲供应链就搜一张物流、仓储或工厂的图；也可以用 SVG 画出产品、物件和场景的示意，例如面料、拉链、鞋服、货车、门店。来源与许可按 [imagery.md](references/imagery.md) 记录。
- **图里基本不放字**：图片和插画不承载大段文字，说明用原生文字放在图旁。数据和关系已经适合用图表、流程图表达的照常用，不为凑图示另造关系图。
- **少字**：页面只留结论标题、关键数字、短标签和改变结论的条件；解释、背景和计算过程放备注。影响观众判断的口径、估算状态和前提，在相关页面用尽可能简短的说明保留；通常一句即可，必要时分别标注。同一句话不在多页重复。关于材料本身的说明（材料没写什么、为什么没画）写在策划稿或备注，不上页面。

**图文均可**：按观众任务选择图、表或文字，允许说明较充分的文字页；图标和配图同样可用。

两种方式都不补造数字、关系、因果或可比性，不丢单位、时点、状态和例外。

## 运行环境

动手前先运行 `python scripts/doctor.py`（只用 Python 标准库）。它报告当前环境的能力，并给出建议路线。按能力选路线，不按 agent 品牌选：

| 能力 | 具备时 | 不具备时 |
|---|---|---|
| 浏览器：Playwright＋Chrome／Edge／Chromium，或 agent 自带的浏览器工具 | `preview.py html` 截图、交互、打印与版面检查 | 只能做 HTML 结构检查，截图、交互和版面检查标为未执行 |
| WPS 或 PowerPoint（Windows） | `preview.py pptx --export wps`（或 `powerpoint`）：由目标软件把最终 PPTX 导出为 PDF，再逐页出图和做版面检查，看到的就是观众看到的换行和字体 | 没有或导出失败时（doctor 只查注册，能否调用以导出结果为准）：用 LibreOffice 渲染（近似），或手动导出 PDF 后用 `--pdf` |
| LibreOffice＋PyMuPDF | `preview.py pptx` 渲染并检查，适合制作中途快速查看；与 WPS／PowerPoint 的换行和字距有差异 | 有 PyMuPDF 时用 `--export` 或 `--pdf`；都没有时 `--edit-test` 仍做对象清点、字体与编辑测试，渲染标为未执行 |
| python-pptx | 新建 PPTX（默认路线，借助 `scripts/pptx_kit.py`：文字、形状、图标、SVG 插画、图表、表格）、模板修改、编辑测试 | 用已安装的其他原生库，例如 PptxGenJS |
| Node.js＋PptxGenJS | 新建 PPTX 的另一选择 | 不必安装 |

agent 特有的能力可以直接复用，例如 Codex 桌面的官方 presentations 环境，或 agent 自带的浏览器与预览面板；预览面板只用于展示，不能替代检查。缺少 Python 包或 npm 包时先说明用途，安装到当前用户或私有构建目录，不修改用户项目的依赖清单。无法安装时报告缺项与受影响的验收项。

## 1. 建立需求与证据

把主题、受众、演示目的、关键内容、篇幅、视觉约束、交付格式和表达方式（用户选择或默认）简短记入策划稿开头。

优先整理用户提供的资料。只有任务需要外部事实、时效信息或用户要求检索时才研究，使用当前环境可用的搜索与阅读工具。数字保留单位、时间、口径和来源；区分事实、计算结果、假设与建议。不能把缺失资料补成确定事实；材料没有给出的比较、转化、因果和可比关系不画、不写。公司模板里的示例文字（日期、部门名、示例标题等）不是材料，列为待确认。

有外部资料或网络图片时保存 `sources.md`，用简短来源标识关联到相关页面和 PPTX 备注。

## 2. 大纲与策划稿

读取 [references/planning.md](references/planning.md)。先决定每页的目的、顺序和能量（高冲击 / 标准 / 密集 / 呼吸），再做视觉设计。报告与说服场景适合结论先行；教学或故事按理解顺序组织，不强套目录和金字塔结构。

必须保存逐页 `planning.md` 并随成品交付；一页任务用短版，修改已有文稿时只更新受影响的页面。策划要写清核心信息、依据、视觉焦点、阅读顺序、版式意图、图片与图标、可编辑对象，不能只有页标题或笼统的风格词。成品改动后同步更新策划稿（页数、页序、主要结论）。

## 3. 定义视觉方向

新建或美化版式时读取 [references/art-direction.md](references/art-direction.md)，并按其指引读取：

- [references/style-recipes.md](references/style-recipes.md)：13 套风格配方，各自写明适用与不适用。有贴切的就选作起点，并结合主题改编色彩、母题和尺度；没有贴切的就按 art-direction 的方法自定方向。
- [references/layouts.md](references/layouts.md)：22 个版式原型，各自写明适用与不适用。作为单页构图的起点，可以修改、组合；没有合适的就自定构图。
- [references/typography.md](references/typography.md)：字体选择与获取、字号阶梯、中文排版、HTML 字体嵌入、PPTX 字体策略。
- [references/anti-patterns.md](references/anti-patterns.md)：平庸与“AI 味”反模式，策划时避开，验收时对照。
- [references/imagery.md](references/imagery.md)：图标、网络图片、生成图、SVG 示意插画，以及没有素材时的图形处理。
- [references/charts.md](references/charts.md)：图表选型与美化默认值，HTML 与原生 PPTX 各自的实现要点。

用户模板、品牌或参考优先。没有参考时，自主确定一个具体的视觉概念，按 art-direction 的格式写进策划稿：概念、配方与改编（或自定）、参考调性、色彩、字体、字号、网格、形状语言、图片与图标处理、高潮页和禁用项。局部文字修改沿用已有视觉体系。

公司模板任务：内容区从模板的版式和占位符取，左右边距与模板一致（左右相等，或分别对齐页眉的标题与标志），并写进策划稿；模板本身有侧栏、图片带或不对称网格时按模板，在策划稿写明依据。在模板之内做到精致，不只是把内容填进占位符。

先决定每页最需要被看见的内容，再选择构图：可以参考适用的版式原型，也可以自定。统一字体、对齐和色彩语义，按叙事安排密度与节奏；为比较而有意重复可以保留。高潮页在策划时就确定，并优先投入。

较长演示（约 6 页以上）先按 [references/visual-review.md](references/visual-review.md) 做方向比较：封面和一个关键页各做 2–3 个明显不同的方向（构图或尺度不同，不只是换色），并排渲染后选定。然后完成代表页，校准后再推广到全套。方向比较和代表页都属于内部步骤，不增加确认关卡，也不增加交付页数。

先让静态画面成立，再按需增加 HTML 动效。文字、图表和需要编辑的对象保持原生。

## 4. 制作交付格式

- **HTML**：读取 [references/html.md](references/html.md)。默认单文件离线可打开。把 `assets/player.css` 与 `assets/player.js` 内联进成品，它们负责翻页、进度、逐步揭示、概览、备注、全屏与打印，不限定页面视觉。图标内联 `assets/icons/` 的 SVG 源码。用 `scripts/embed_fonts.py` 子集化并内联设计字体。
- **PPTX**：读取 [references/pptx.md](references/pptx.md)。新建用 python-pptx 时借助 `scripts/pptx_kit.py`：`icon()` 把图标做成可改颜色的原生形状，`svg_picture()` 把 SVG 插画转成高清图片插入。正文、表格、数据图表及要求可编辑的示意图使用原生对象。按 typography 为每段文字设置中文东亚字体。公司模板保留母版、版式、占位符与主题，默认不运行全局字体覆盖。
- **两者都要**：共享页数、顺序、核心文字、数据与视觉规则，分别制作、分别验收。不把 HTML 截图或整页 SVG 塞进 PPTX 当作可编辑交付。

## 5. 实际预览验收

**生成文件、解析成功、代码检查和模型评分都不能替代实际看图。** 制作或美化页面时读取 [references/visual-review.md](references/visual-review.md)。

1. 对照策划稿检查内容覆盖、总页数、事实、单位和引用；移除未解决的占位与制作过程文案。
2. HTML：`preview.py html` 实际打开最终文件，逐页截取完全揭示的页面，检查离线、字体图片、翻页、打印和窄视口。
3. PPTX：重新读取最终文件并逐页渲染。电脑上有 WPS 或 PowerPoint 时，用 `preview.py pptx --export wps`（或 `powerpoint`）由目标软件导出 PDF 再检查；没有时用 LibreOffice，并在记录中写明是近似。
4. **看两遍**，两个命令都加 `--zoom`：
   - 第一遍看整页：版心和左右边距是否对齐模板或页眉，主次、留白、图片与图标是否成立，整套节奏是否单调。
   - 第二遍看 `zoom/` 里的放大局部：文字有没有跑出卡片或底框、孤字、断行、数字与单位分开、线条穿字、图片裁切。
5. 版面检查的错误必须修复；警告（孤字、文字跑出框、线条穿字、版心偏一侧等）逐条看图确认，有意的写明理由。图示优先时加 `--visual-first`，它指出过长的段落、文字卡片和字多的页面：逐条处理，删重复、移到备注，或改用图标、图片承担，不靠删条件降字数，也不用一句话统一豁免。
6. 编辑测试：`preview.py pptx --edit-test` 在副本中修改代表性的文字、表格、图表、分组和图片，保存、重开、核对。最终文件不保留测试改动。
7. 记录只写实际做过的检查：编辑测试按报告里的对象类型和数量写，没有的对象不写成测过；LibreOffice、WPS、PowerPoint 的渲染与操作分别如实写。看图部分写发现的问题、修改和复查结果，不能只写“通过”。
8. 修复后重新导出并查看受影响的页面；全局字体、配色或间距改变时重新查看全套。两种格式各自通过才算双格式完成。
9. 底线都通过后，按 visual-review 的“出彩检查”自查高潮页和整套辨识度，有具体可改之处就改。

缺少浏览器、渲染器或导出能力时，保留已完成的产物，明确指出哪项验收尚未完成；不得悄悄改成交付整页图片，不得声称已完成实际预览。

## 6. 交付

交付用户需要的 `index.html`、`deck.pptx` 与 `planning.md`，用了外部资料或网络图片时附 `sources.md`；PPTX 使用非系统字体时附字体文件或安装说明。生成源码、截图和验收记录留在私有构建目录，用户要求时再交付。保持策划稿与最终版本一致。

简短说明完成的格式和使用方式（例如 HTML 的快捷键），提供真实的绝对路径；有影响使用的限制时准确说明。agent 自带的预览面板可以展示成品，但不算完成预览验收。达到当前要求后停止。
